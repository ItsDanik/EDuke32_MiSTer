# EDuke32 hybrid core for MiSTer (Duke Nukem 3D)

@hybrid/CLAUDE.md

## This core

- Name everywhere: `EDuke32` (the engine: core, folders `games/dnk/EDuke32/` and `logs/dnk/EDuke32/`, `_Other/dnk/dnk-EDuke32_*.rbf`, release), `eduke32` (game submodule, binary in `build/`, log, lock). The games and their menu entries (`_Other/dnk-<title>.mgl`): `package/games.txt` (in the zip as `games/dnk/EDuke32/games.txt`, from which the database's build makes the launcher's catalogue).
- The game is the `eduke32/` submodule, branch `mister`. Its MiSTer code is behind the `MISTER_HYBRID` build option.
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Release: the zip in `releases/`. Players get it once it is published to the database, only when Danik asks: `hybrid/launcher/distribution.py publish ~/dnk_Distribution_MiSTer releases/EDuke32_YYYYMMDD.zip` (the rule in `hybrid/CLAUDE.md`).
- Try a build on the MiSTer without installing it: `MISTER=root@<address> tools/test_on_mister.sh <id>|list|nodata|log|stop` (the rule in `hybrid/CLAUDE.md`).
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

## EDuke32

- The game is [EDuke32](https://voidpoint.io/terminx/eduke32) (`eduke32/`, from upstream master ec5824db8, branch `mister` local only for now: no fork on GitHub yet, Danik, 2026-10-24). GPL-2.0 only, so `hps/` was relicensed GPL-2.0-or-later for it (hybrid 7a95eb1). New files of ours in it carry `SPDX-License-Identifier: GPL-2.0-or-later`; modified Build sources already carry Ken Silverman's notice (`BUILDLIC.TXT` ships under that name, as its licence asks).
- `MISTER_HYBRID=1` (`Common.mak`, `GNUmakefile`): classic 8-bit renderer only, no OpenGL / Polymer / network / GTK / VPX / FLAC / ALSA, SDL static. The game's part is `source/duke3d/src/mister_port.cpp` (games, OSD options, cheats, HUD margins, exit codes); the engine's `source/build/include/mister.h`, `sdlayer.cpp` (video, joystick, rumble, drawing ahead), `timer.cpp` (the field clock), `engine.cpp` (2D art at 240 lines), `baselayer.cpp` (`engineFPSLimit()`).
- Games (`package/games.txt`): DN3D (shareware DN3DS falls back to it), DC, VACA, NW, DZ2, PP (the last two since 2026-10-25, Danik), each known by its GRP's CRC (`Games[]` in `mister_port.cpp`, in order of preference). Under MiSTer `FindGroup(DUKE15_CRC)` also takes the Plutonium Pak (1.4), so the Atomic add-ons run with 1.4 too. Duke!ZONE II: Raze's release (`DUKEZONE2.GRP`, a zip of 21 levels in three episodes, CRC 0x3B29D5C7) is in `grpscan.cpp`'s table under `MISTER_HYBRID` (upstream knows it only from the `DUKEZONE2.GRPINFO` next to it) besides upstream's three CD versions; Penthouse Paradise: its original `penthous.zip` (opened as a group file, kplib) or ZOOM Platform's GRP. An add-on that only a player's own `.grpinfo` describes is in the list, without a menu entry. Megaton Edition's `addons/dc`, `addons/nw`, `addons/vacation` are search paths (`G_AddMiSTerSearchPaths()`, called also with `-usecwd`). No NAM / WWII GI (Danik, 2026-10-23).
- Saved games: Duke Nukem 3D's in the game's folder as upstream (`save0000.esv`), each add-on's in a folder named by its id (`DC/`, `VACA/`, `NW/`, `DZ2/`, `PP/`; an add-on of the list by its GRP's name): `MiSTer_SaveDir()`, `savegame.cpp`. Otherwise every game listed (and some could load) the others' saves. Settings (`eduke32.cfg`, `settings.cfg`) are shared by all games. The game's own log file is not written with the core (the launch script keeps stdout); controller bindings of a saved `eduke32.cfg` are not read with the core, the MiSTer defaults are set at every start (`CONFIG_SetupJoystick()`).
- Controls (Danik, 2026-10-23: "jfSW's, Duke flavour"): J1 Fire, Open, Jump, Crouch, Next Weapon, Use Item, Map, Menu, Menu OK, Menu Back; jn R,B,A,L,Y,X,Select,Start. The core's joystick is shown to the game as a game controller (`misterJoyUpdate()`): A / B are Menu OK / Back alone (the menus take them), the J1 actions are on buttons the menus do not read. R2 Fire, L2 and R3 Quick Kick, L3 AutoRun, d-pad walk and turn. Use Item held + d-pad left / right selects the item (`MISTER_CB_ITEMLEFT` / `RIGHT`), let go without the d-pad it is used (an 80ms press). A press the game cleared stays up until let go (`takenBits`), else the menu opened and closed on one press of Start. The menus clear walking and turning too (`I_Menu*Clear()` in `input.cpp`), else a held d-pad moved them every frame. The quit question says "Menu OK: accept, Menu Back: return.".
- OSD (status bits): 24..25 Resolution, 26..28 / 29..31 stick sensitivity (on top of the game's), 32 Limit Vertical Look (half the range, On by default), 33..34 Rumble On / Strong / Off (On by default; the game's own rumble option is hidden), Cheats 35 God, 36 No Clipping, 37 Show Full Map, 38 No Monsters, triggers 56 Everything, 57 Weapons, 58 Keys, 59 Next Level (Danik, 2026-10-23: all of them). Cheats as the game's: not at skill 4, in a demo, a user map or multiplayer. The game's video mode menu and its sound device / sampling rate / OPL / SoundFont lines are hidden with the core.
- HUD margins (Danik, 2026-10-23): both edges. *HUD (Bottom)* moves the status bar, the mini HUD (and the inventory) and the weapon (`MiSTer_HudDown()`, `MiSTer_HudBottom()`), *HUD (Top)* the quotes, the level's name and the frag bar (`MiSTer_HudUp()`), through `MISTER_HUD()` around their drawing in `screens.cpp`, which sets `rotatesprite_mister_yofs`. At 240 lines the status bar is drawn over the view (`MiSTer_StatusBarOverlay()`), redrawn every frame. Both lines greyed out at 200 lines (menu mask bit 0).
- Music: MIDI in the GRPs. With *Music* on MIDI (and `MH_MidiWanted()`) the game's own SF2 path sends to the synthesizer / MT32-pi; FM chip: `driver_misterfm.cpp` (jfSW's driver, the Apogee AdLib driver with the GRP's `D3DTIMBR.TMB`), the `ASS_MisterFM` device picked by `MUSIC_Init` autodetect, advanced from `fillData` in `driver_sdl.cpp`.
- Drawing ahead (`MISTER_DRAW_AHEAD` in `sdlayer.cpp`, `misterField()`) is in the engine and switched **off** (0). Benchmark on the MiSTer (2026-10-24), 640x240, a demo of E1L1 Danik played and recorded on the MiSTer (`-r -v1 -l1 -s2`, played back with `-dedemo001.edm`; a demo from the 64-bit PC build does not play on the 32-bit ARM), `MISTER_HYBRID_PACE=1`, 25 windows of 300 frames each, in turns: drawing ahead never shown 24 / shown twice 154, the old way (`MISTER_HYBRID_AHEAD=0`) 19 / 144, drawing ahead 23 / 154, the old way 13 / 145. About 100 of the shown twice are the first two windows, the level loading; after that 0 to 9 per 300 either way, frames up to 15 to 17ms into a field. Drawing ahead is no better, so the old way, with one field less latency.
- Speed on the MiSTer (2026-10-24, the same demo at 640x240): the frame's work went from 13 to 15ms (up to 22) to 8 to 10ms (up to 17), every frame of the demo shown at the next field (`MISTER_HYBRID_PACE=1`: 38 windows of 300 in a row, "later 0", at most 6ms into a field; only the first frame after the level's loading is late). What it took, each for the MiSTer alone (`MISTER_HYBRID`, `__arm__`): the Cortex-A9 has no integer division, and libdivide's divider for every new divisor cost 1.5us, 11% of all the time: `tabledivide64()` takes the FPU's quotient made exact (`misterdivide64()`, `pragmas.h`), `tabledivide32()` libgcc's (results checked the same as C's on millions of inputs). The column and span loops (`a-c.cpp`): four columns at once kept most of their registers on the stack; `vlineasm4()` draws two at a time, `mvlineasm4()` one, `hlineasm4()` without its slice by 4, in ARM code (`MISTER_ARM_CODE`), the same pixels in about two thirds of the time. `distrecip[]` (`engine.cpp`), made again when the view's width changes (the first camera screen), by its quotients one from the last instead of 115,000 divisions (15 to 25ms). A demo: its art precached as in a game (`G_CacheMapData()`), and its state of every two seconds not loaded (`demoplay_diffs` 0, 15 to 20ms each; a demo of the same build stays in step without).
- `HIGH_PRECISION_SPRITE` (`engine.cpp`), which upstream leaves out on ARM, is on under `MISTER_HYBRID` (2026-10-25): without it a sprite's texture row overflowed with the view tilted up and the drawing read other columns of the tile (E1L1's "Innocent?" billboard striped by its own frame, the stripes moving as the view turned, at every resolution). Found by putting the host build at the same position (`dncoords` on the MiSTer): it drew the billboard right, the MiSTer with its ARM division and column loops switched back to upstream's did not. Still 60 there.
- Profiling: `rm -rf build/mister/obj; MISTER_PROFILE=1 ./build.sh` (the release with its symbols; remove the objects again after). It prints every frame that missed a field with the time of its parts, and every 300 frames their averages and maxima (`mister.h`, `MISTER_PROF_SCOPE`), and samples the game thread 1000 times a second into `/tmp/eduke32_prof.bin` (pc and lr, a mark of ~0 and the frame's fields and work after each frame), which `nm -n` of the binary resolves.
